# qrtoss UI/UXデザイン設計書

## 1. 目的

本書は、qrtoss WebアプリケーションのUI/UXをゼロから設計・実装するための仕様を定義する。画面構成、視覚表現、操作、レスポンシブ対応および受け入れ基準を対象とする。

デザインコンセプトは、**シンプルで洗練された、完全モノクロのフラットデザイン**とする。

初めて利用するユーザーが、接続用QRコードの読み取り、送信内容の確認、受信という流れを理解でき、PCとスマートフォンの両方で快適に操作できることを目標とする。

UIはHTML/CSSと必要最小限のフロントエンドコンポーネントで構成する。通信・セキュリティの契約は [プロトコル仕様書](spec.md) に従い、本書ではその視覚表現と操作方法を定義する。

## 2. デザインの基本方針

### 配色

完全なモノクロデザインとする。

- 背景：白（#FFFFFF）
- 主要テキスト：黒に近い色（#171717）
- 補助テキスト：濃いグレー（#525252）
- 境界線：薄いグレー（#D4D4D4）
- 選択状態：黒い境界線と淡いグレーの背景
- 無効状態：薄いグレー

以下は使用しない。

- 色相のあるアクセントカラー
- グラデーション
- box-shadow、text-shadow
- 装飾的な背景模様や図形
- 不必要なアニメーション
- 過度な角丸や立体的な表現

色ではなく、タイポグラフィ、余白、整列、線の太さ、明暗差によって情報の階層を表現する。

### フラットデザイン

- カードは白背景と1pxの境界線で構成
- 角丸は8〜12px程度に統一
- ボタンや選択項目もフラットにする
- アイコンは単色の線画で統一
- 装飾的な要素は極力排除
- 必要な情報と操作要素だけを表示

Appleのシンプルな設定画面やモダンな開発者向けツールのような、機能的で落ち着いたデザインを目指する。

## 3. タイポグラフィ

フォントはUDフォントを優先し、利用できない環境ではシステムのサンセリフ体へフォールバックする。日本語・英語・スペイン語の可読性を確保する。

文字サイズの目安：

| 要素 | サイズ |
|---|---|
| ページタイトル | 20〜22px |
| カード見出し | 20〜22px |
| 本文・操作項目 | 16〜18px |
| 補助テキスト | 14〜15px |
| ボタン | 16px |
| 接続状態・有効期限 | 14〜16px |

- 小さすぎる文字をなくす
- 過度に細い文字や薄い文字を避ける
- 行間を適切に設定する
- 見出しと本文の太さを統一する
- 日本語と英語の両方で読みやすいこと
- 画面に収めるために文字サイズを極端に小さくしない

## 4. ヘッダー

ヘッダーはコンパクトな1行構成にする。

### 左側

- qrtossのロゴ
- ロゴも完全モノクロにする
- ロゴは右上向き矢印のシンボルと「qrtoss.」のワードマークで構成する

### 右側

以下の順序で配置する。

1. GitHubへのリンク
2. 言語選択メニュー

GitHubリンク：

https://github.com/kodogu-works/qrtoss

表示仕様：

- GitHubアイコンと「GitHub」の文字を表示
- 背景や装飾的な枠線は付けない
- 新しいタブで開く
- `target="_blank"` と `rel="noopener noreferrer"` を指定
- `aria-label` を設定
- hover時は下線またはグレーの変化で示す
- モバイルではアイコンのみの表示でもよい

ヘッダーの高さは56〜64px程度を目安にする。

## 5. ページタイトル

受信画面のページタイトルは「この端末で受信」とする。タイトル周辺にはキャッチコピーや導入文を配置しない。各言語では同じ意味の翻訳を表示する。

表示仕様：

- フォントサイズ：20〜22px
- 左寄せ
- カード見出しと同程度のサイズ
- カードの左端と揃える
- 上下の余白を最小限にする
- タイトルとカードの間隔は16〜24px
- 中央寄せにしない
- 装飾的な線やラベルは追加しない

## 6. メインレイアウト

### デスクトップ

受信画面は2カラム構成とする。

**左カラム：スマホを接続**

- 接続状態
- QRコード
- 有効期限
- 更新操作
- 必要最小限の操作説明

**右カラム：受信設定と受信内容**

- 受信後の動作の選択
- 受信した内容の表示

左右のカードの上端を揃え、余白と境界線を統一する。

### 一画面表示

デスクトップでは、通常のブラウザ表示領域内に全操作要素が収まるようにする。

特に以下の表示サイズで検証する。

- 1440×900
- 1280×720
- 1024×768

実際のブラウザの表示領域（viewport）を基準にする。

対応方針：

- ヘッダーとタイトル領域をコンパクトにする
- カード内の不要な余白を削減する
- QRコードのサイズを画面高に応じて調整する
- QRコードは原則180〜260px程度を目安にする
- QRコードの周囲には読み取りに必要な余白を確保する
- 空の受信内容表示領域はコンパクトにする
- CSSの`clamp()`、`min()`、`max()`、viewport単位などを適切に利用する
- `overflow: hidden`でコンテンツを隠して一画面表示を実現しない
- 文字の可読性やQRコードの読み取りやすさを犠牲にしない

画面が極端に小さい場合は、無理に一画面表示を強制せず、スクロールを許可する。

### スマートフォン

- 1カラムレイアウトに切り替える
- カードは縦方向に配置する
- 横スクロールを発生させない
- QRコードを十分なサイズで表示する
- 文字サイズを維持する
- タッチ操作領域を44×44px以上確保する
- 必要な縦スクロールは許容する
- 画面幅に応じて余白を調整する

## 7. QRコードと接続状態

QRコードは左カラムの中心的な要素として表示する。

- QRコードは水平中央に配置
- 周囲に十分な白い余白を確保
- QRコードの視認性と読み取りやすさを維持
- 接続状態は文字とアイコンで明確に表示
- 色だけで状態を区別しない
- 有効期限を読みやすく表示
- 更新操作をわかりやすく配置
- 接続準備中、接続待機中、接続確認中、接続完了、切断、期限切れを表示する。送信側の読み取り中・送信待ち・受信完了も文字で通知する

状態表示は過度に目立たせず、必要な情報を簡潔に示する。

## 8. 受信後の動作選択

受信後の動作は、以下の2つから選択する。初期選択は「Webページを自動で開く」とする。

- Webページを自動で開く
- 内容を表示

操作仕様：

- ラジオボタンとテキストを明確に配置
- 選択項目全体をクリック・タップ可能にする
- 選択中の項目は黒い境界線などで強調
- 選択していない項目は薄いグレーの境界線
- 説明文は必要最小限にする
- 選択状態を色だけに依存させない
- キーボードでも操作できるようにする

## 9. 受信内容の表示

受信内容がない場合：

- 空の表示領域をコンパクトにする
- 「受信した内容がここに表示されます」などの簡潔な案内を表示
- 不必要に大きな空白を作らない

受信内容がある場合：

- 内容を読みやすく表示
- 長いテキストやURLでもレイアウトが崩れないようにする
- コピー、内容の消去、および内容の種類に応じた手動のWebページ・対応アプリ起動を提供する
- コピー結果は受信内容の近くに表示する。クリップボードを利用できない場合は手動コピーの案内を表示する
- 受信内容をHTMLとして解釈せず、文字列として表示する
- 必要に応じて受信内容領域内でスクロールできるようにする

## 10. UIコンポーネントの統一

以下のスタイルを共通化する。

- カード
- ボタン
- ラジオボタン
- 入力欄
- セレクトメニュー
- ステータス表示
- アイコン
- 区切り線

CSS変数などを利用して、色、文字サイズ、余白、角丸、境界線を一元管理する。

共通スタイルを再利用し、同じ役割のコンポーネント間で表現を揃える。

## 11. アクセシビリティ

- 十分な文字コントラストを確保
- キーボード操作に対応
- focus状態を明確に表示
- ボタンや選択項目に適切なラベルを設定
- 必要な箇所にARIA属性を設定
- 状態変化をスクリーンリーダーにも伝える
- 色だけに依存しない状態表示
- `prefers-reduced-motion`を考慮

## 12. 機能・通信との境界

UIは以下のアプリケーション機能を利用する。具体的な通信方式、許可されるURL、有効期限およびエラーの判断は [プロトコル仕様書](spec.md) に従う。

- 接続用QRコードの生成と端末間の接続
- WebSocketおよびDurable Objectsを介した通信
- API呼び出し、セッション管理、有効期限管理
- 受信後の自動遷移または内容表示
- 暗号化、接続情報の保護、エラーハンドリング
- 日本語・英語・スペイン語の言語選択

表示層はアプリケーションの状態を受け取り、操作要求を伝える。レイアウトや表示上の都合で、通信契約、セキュリティ条件、有効期限を変更しない。デザイン表現のための依存ライブラリ追加は原則として不要とする。

### 送信画面

送信画面は共通ヘッダーと1カラムのカードで構成する。ページタイトルは「スマホから送信」とし、以下の順で情報を配置する。

1. 接続状態と受信側の動作モード
2. カメラ利用の説明、読み取り中のカメラ映像、または読み取り済み内容のプレビュー
3. 状態に応じた読み取り開始、停止、送信、再読み取り、送達再確認、コピーの操作

カメラはユーザーの読み取り操作で開始する。読み取り後は内容を確認でき、送信操作によって転送する。操作の可否は接続・読み取り・送達の状態に従い、利用できない操作は無効化または非表示にする。接続エラーとカメラ権限エラーは、理由を文字で案内する。

## 13. 検証と受け入れ基準

Playwrightなどを利用して、実際のブラウザで表示と操作を確認する。

対象サイズ：

| 画面サイズ | 主な確認事項 |
|---|---|
| 1440×900 | 全体が一画面に収まる |
| 1280×720 | 縦スクロールが発生しない |
| 1024×768 | 文字とQRコードの可読性 |
| 390×844 | モバイルレイアウト |
| 375×667 | 小型スマートフォン |

確認事項：

- レイアウト崩れがない
- 文字が小さすぎない
- 横スクロールが発生しない
- QRコードを読み取れる
- ボタンと選択項目を操作できる
- 接続状態が正しく表示される
- 受信内容が正しく表示される
- 日本語・英語・スペイン語でレイアウトが崩れない
- GitHubリンクが正しく動作する
- 接続、送信、受信、コピー、自動遷移、期限切れ、エラー処理がプロトコル仕様に従って動作する

## 14. 実装構成と設計の適用

画面の責務を、共通の画面構造、スタイル、翻訳、受信状態、送信状態に分ける。色、文字サイズ、余白、角丸、境界線は共通のデザイントークンで管理する。

実装は以下の順序で組み立てる。

1. デザイントークンと共通コンポーネントを定義する
2. 共通ヘッダーと受信・送信画面の構造を作成する
3. 接続状態、選択状態、空表示、受信内容、エラー表示を実装する
4. アプリケーションの状態と操作を画面に接続する
5. レスポンシブ配置、多言語、キーボード操作、読み上げを整える
6. 第13節の受け入れ基準を検証し、表示と操作を調整する

## 15. デザインの到達基準

**完全モノクロ、フラット、コンパクト、読みやすいUI。**

- 白い背景
- 黒い文字
- 薄いグレーの境界線
- UDフォント
- 装飾を最小限にしたヘッダー
- 左寄せの小さなページタイトル
- 左にQRコード、右に受信設定
- デスクトップでは一画面に収まる
- スマートフォンでも直感的に操作できる
- GitHubリンクをヘッダーに配置

機能性と可読性を最優先し、余計な装飾のない、シンプルで洗練されたWebアプリケーションにする。
